# 패미콤 한글화에서 얻은 교훈

이 문서는 Gun Nac 한 작품에서 관찰한 사실과 다른 작품에 적용할 수 있는 절차를 구분합니다. 메모리 주소, 여유 공간, 호출 규약은 다른 게임에서 다시 조사해야 합니다. 폰트가 비슷하다고 렌더러나 매퍼 동작까지 같지는 않습니다.

## 1. 번역 전에 정확한 입력과 출력 경로를 확정한다

ROM 이름만 기록하지 말고 파일 전체 크기, 헤더 포함 여부, CRC32·MD5·SHA-1·SHA-256을 함께 남깁니다. 다른 리비전이나 헤더가 다른 파일에 같은 주소 패치를 쓰면 조용히 잘못된 곳을 바꿀 수 있습니다. 입력을 검증하고 예상 원본 바이트가 다르면 중단하는 것이 기본입니다.

번역된 타 언어판은 변경 지점을 찾는 참고 자료가 될 수 있지만, 최종 기준은 의도한 원본 판으로 고정합니다. 타 언어판이 합친 페이지나 달러로 바꾼 통화를 그대로 가져오면 원문 기반 번역과 어긋납니다.

일반 문자열, 타일 그림, 스프라이트 글자, 동적 숫자, 로고를 분류합니다. Gun Nac에서는 본문은 배경 타일이지만 스테이지 이름은 8×16 스프라이트였습니다. CHR에 글자가 있다고 모두 같은 문자열 루틴으로 출력되는 것은 아닙니다.

## 2. 주소와 문장을 분리한 작업표를 만든다

원본 파일 주소를 안정적인 ID로 쓰고, 원문·번역·화면 위치·동적 토큰·검토 상태를 구분합니다. 재추출은 승인 번역을 덮어쓰지 않아야 합니다. 공개할 때는 일본어 원문과 원본 바이트를 제외하고, 사용자의 로컬 ROM에서 다시 추출할 수 있게 합니다.

의미 중심으로 번역합니다. 이 작업에서 원소/천체 이름을 한자의 음으로만 옮기지 않고 ‘불의 별’, ‘물의 별’, ‘돈의 별’처럼 게임 맥락과 함께 검토했습니다. 주소가 같아도 문맥은 실행 화면에서 확인해야 합니다.

문구와 줄바꿈을 분리합니다. 번역이 바뀌었는데 예전 줄바꿈 파일을 그대로 사용하면 이전 문장이 되살아나는 문제가 생깁니다. 두 파일을 공백 제외 기준으로 비교해 내용 차이가 생기면 빌드를 멈췄습니다.

## 3. 한글 가독성은 글자 수와 타일 수를 함께 본다

게임의 원래 8×8 한글 칸에 억지로 받침까지 압축하면 읽기 어렵습니다. 화면과 PPU 용량이 허용하면 두 타일 높이(8×16) 본문, 16px 제목을 먼저 시험합니다. 폰트 이름과 크기만으로 판단하지 말고 실제 1배 화면에서 ‘흙’, 받침이 많은 글자, 띄어쓰기, 숫자, 기호를 함께 비교합니다.

원본 BDF의 픽셀을 직접 사용하면 운영체제별 안티앨리어싱 차이를 피할 수 있습니다. baseline, BBX 오프셋, 글리프별 폭, 그림자 자리, 인코딩 실제 값을 검사합니다. BDF 헤더 표기와 ENCODING이 다르거나 BITMAP 줄에 공백이 붙는 사례도 있었습니다.

사용한 글자 수와 필요한 CHR 타일 수는 다릅니다. 비어 있는 조각, 같은 상하·좌우 조각을 공유하면 용량이 줄어듭니다. Gun Nac의 제목은 13글자를 48개 타일에 넣었습니다. 공유 여부는 실제 비트맵으로 결정해야 합니다.

## 4. 원본의 굵기를 글꼴 혼합 정책으로 보존할 수 있다

갈무리 영문으로 일괄 교체하거나 모든 글자를 인공 볼드로 만들면 원본의 강조가 달라집니다. 여기서는 한글은 갈무리, 확인된 영문·숫자·기호는 원본 ROM의 글꼴을 재사용했습니다. 서로의 baseline을 맞춰 ‘B2’ 정책으로 고정하고 문자 집합도 명시했습니다.

원본 글꼴을 재사용한다고 해서 원본 폰트 덤프를 저장소에 넣을 필요는 없습니다. 빌드 중 로컬 ROM에서 필요한 패턴을 읽으면 됩니다. 공개 소스와 생성 에셋을 나누는 데도 도움이 됩니다.

## 5. 줄바꿈은 공백 수가 아니라 렌더러의 행 단위로 판단한다

상점 안내의 ‘주의해 주세요’가 한 줄 떨어져 보인 사례는 번역 내용보다 배치 좌표의 문제였습니다. 한글 한 줄이 PPU 두 타일 행을 차지한다는 점을 레이아웃에 반영해야 합니다.

짧아진 문자열 뒤에는 이전 문장의 잔상이 남을 수 있습니다. 새로운 문장 길이만큼만 덮지 말고 기존 표시 영역의 상하 행을 모두 지웁니다. 배송 목적지가 비어 있을 때 이전 목적지의 설명을 지우는 경우도 같은 문제입니다.

수량과 금액은 서로 다른 정렬 기준을 가집니다. 이 작업은 ‘개/회’ 앞 숫자를 정렬하고, 가격은 ‘엔’을 기준으로 정렬했습니다. 1·9·10·20·63 같은 경계값, 단위 변경, 금액 부족 표시를 실제 값으로 시험합니다.

## 6. ROM 확장은 메모리 배치의 변경이다

헤더의 PRG/CHR 크기만 늘려서는 끝나지 않습니다. MMC3의 고정 끝 뱅크, 명시적 뱅크 번호, 1 KiB와 2 KiB CHR 레지스터의 차이, 원래 뱅크 복구, NMI/IRQ에서 보이는 코드를 함께 확인해야 합니다.

본 프로젝트는 고정 PRG 뱅크를 새 끝으로 옮기고 이전 사본도 보존했습니다. 화면 계열별로 폰트를 나누었고, 원래 호출 지점에 짧은 연결 코드를 넣었습니다. 새 코드가 비어 보이는 원본 데이터에 들어갈 때도 그 데이터가 정말 더 이상 사용되지 않는지 확인하고 경계를 검사했습니다.

`$FF`가 길게 이어진 영역은 여유 공간의 후보일 뿐 증명이 아닙니다. 사용 경로와 범위를 조사하고, 빌드 시 기존 바이트·주입 크기·다른 주입물과의 간격을 검사하세요.

## 7. 그림을 조금 옮겨도 IRQ·스크롤·팔레트가 따라온다

자막을 그림 아래에 놓으면 본문·스태프롤과 겹칠 수 있습니다. 위쪽 자막도 원래 여백이 충분한지 확인해야 합니다. 16px 자막을 줄이는 것보다 세 엔딩 그림을 16px 옮기는 편이 읽기 좋았습니다.

그림만 내렸다고 끝나지 않았습니다. 그림용 CHR에서 글꼴용 CHR로 바뀌는 IRQ 위치가 그대로면 아래쪽 그림이 잘릴 수 있습니다. 반대로 IRQ를 늦추면 하단 로고가 함께 이동할 수 있어 하단 스크롤 원점도 보정했습니다.

원본 그림이 사용하는 팔레트와 타일을 조사한 뒤 자막을 넣습니다. 엔딩에서는 안 쓰던 팔레트를 활용했지만 오프닝은 같은 방법이 그림 색을 바꿀 수 있어 기존 회색 그림자를 유지했습니다. ‘같은 자막 디자인’보다 원래 그림의 색상 보존이 우선인 화면도 있습니다.

## 8. 예쁜 한 장의 캡처는 하드웨어 검증이 아니다

스테이지 이름 정지 화면은 모두 정상으로 보였지만 다음 프레임에서 획 일부가 사라졌습니다. 원인은 스캔라인당 8개 스프라이트 한도와 별 배경, 매 프레임 바뀌는 표시 순서였습니다. 한글 네 글자면 스프라이트 여덟 개를 모두 사용하므로 배경 별까지 고려해야 합니다.

이름 표시 중에만 글자가 먼저 표시되도록 하여 해결했고, 각 구역 229개 연속 프레임에서 획·그림자 픽셀을 확인했습니다. 같은 높이의 배경 별 일부는 생략될 수 있다는 절충을 문서화했습니다. 에뮬레이터의 스프라이트 한도 해제 옵션으로 현상을 숨기는 것은 해결이 아닙니다.

스태프롤도 한 장만 보지 않고 8개 세로 픽셀 위상을 확인했습니다. 화면 전환 직전/직후, 긴 문자열에서 짧은 문자열로 변경, 마지막 로고, 다음 게임 화면까지 보는 것이 중요합니다.

## 9. 게임 상태와 표시 결과를 따로 검증한다

원본과 한국어판에 같은 입력·명시적 테스트 상태를 주고 잔액, 무기 단계, 배송 재고, 커서 선택 결과를 비교합니다. 표시가 맞아도 숫자를 넘겨주는 스택이나 뱅크를 훼손하면 실제 구매 결과가 달라질 수 있습니다.

설정의 불리언은 0/1만 온다고 가정하면 안 됩니다. 원본이 0/비0으로 처리하는 값을 테이블 인덱스로 바로 쓰면 `$FF`에서 깨집니다. 원래 의미를 보존한 뒤 출력용 값으로 정규화합니다.

테스트용 엔딩 직행 ROM과 RAM fixture는 배포 입력과 엄격히 구분합니다. 정상 플레이 클리어를 하지 않았다면 ‘전 구역 클리어 검증 완료’라고 쓰지 않습니다. 핵심은 재현 가능한 테스트와 검증 범위를 정직하게 남기는 것입니다.

## 10. 배포 준비를 마지막 파일 복사로 끝내지 않는다

IPS는 확장된 ROM 영역에 복사한 원래 PRG·CHR도 담을 수 있습니다. ‘패치라서 원본 에셋이 없다’는 가정은 틀립니다. 생성 IPS, 스크린샷, 역어셈블 전체 덤프, 폰트 타일 시트까지 별도로 분류해야 합니다.

이 프로젝트는 소스·한국어 표·주소 정보·노하우만 공개하도록 준비했습니다. 입력 폰트는 고정 커밋과 해시로 외부에서 받고, 원문·원본 그래픽·폰트 패턴은 로컬에서만 생성합니다. 업로드 대상은 확장자 제외 목록뿐 아니라 명시적인 파일 목록으로 제한합니다.

마지막에는 그 목록만 새 폴더에 복사해, 기존 중간 파일 없이 처음부터 빌드합니다. 출력 ROM과 IPS가 기존 검토판의 해시와 같아야 ‘다른 사람이 재생성할 수 있는 소스’라고 할 수 있습니다.

## 다른 작품용 기록 양식

새 프로젝트에서 아래 항목을 채우면 이번 경험을 재사용하기 쉽습니다.

- 대상 판본·네 가지 파일 해시·헤더 및 매퍼·PRG/CHR 크기.
- 화면 목록, 텍스트/그림/스프라이트/동적 값 구분, 원본 유지 결정.
- 레코드 ID, 포인터 위치, 종료 명령·줄바꿈 명령, 뱅크와 주소 변환.
- 글꼴 출처·고정 버전·실제 픽셀 크기·baseline·사용 타일 수.
- RAM 필드의 원래 의미·범위·0/비0 여부·호출 시 보존할 값.
- IRQ 경계·PPU 큐 한도·팔레트 공유·스프라이트 한도.
- 주입 범위·확장 전략·복구 코드·빌드 시 검사.
- 정상 입력/fixture 구분, 프레임별 화면 검사, 상태 비교, 아직 안 한 테스트.
- 공개 파일 목록, 외부 입력 준비 방법, 소스만으로 한 재빌드 결과.
